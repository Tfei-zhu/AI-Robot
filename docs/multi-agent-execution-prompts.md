# 多 Agent 实施流程与防错提示词

日期：2026-10-17。对应计划：`docs/multi-agent-implementation-plan.md`，基线提交 `1ea7e6b`。

本文件是给开发助手 Codex 的执行指令模板，供用户后续发起开发时使用。文中的主 Agent 和代码子 Agent 是 AI-Robot 产品内的组件。这是历史执行模板，不是实现状态清单；S0–S9 的当前结果见 multi-agent-delivery-audit.md 和执行记录。

“易错点”是基于当前代码和任务结构的风险判断，不代表对助手错误频率的统计。提示词只能降低遗漏概率；关键限制还要落实为服务端规则、自动检查和实际运行证据。

**使用方法**

推荐首次发送“总控提示词 + S0”，之后按 S1 至 S9 逐步执行。每一步都包含阅读现状、实施、针对性验证、修复和记录；阶段内可自行完成的修复继续执行，无需反复请求用户确认。若希望连续执行，可使用文末的连续执行提示词。

每次开始都重新核对当前代码状态和执行记录；不要只凭聊天摘要或原计划的“待执行”字样判断进度。每步通过后才推进依赖它的工作；环境阻塞时继续完成不依赖该环境的任务，并清楚保留待验证项。

| --- | --- | --- | --- |

**每一步共用的总控提示词**

```text
请在 /Users/xumanchun/Documents/agent项目/AI-Robot-latest 中，依据
docs/multi-agent-implementation-plan.md 和
docs/multi-agent-execution-prompts.md 实施我指定的步骤。

开始前读取适用的仓库说明、计划、当前 git 状态和已有执行记录。
以代码和已保存证据确认当前进度，保留已有本地改动。
旧项目目录只用于分析和选择性复用，不直接覆盖新版文件。

执行方式：
1. 简短说明本步目标、依赖、改动范围和验收条件，然后直接实施。
2. 当前步骤内自行修复能解决的问题，完成针对性验证；不要只停留在方案。
3. 每步同时补必要的行为测试，不把所有验证推迟到最后。
4. 发生失败时先定位原因；不得为了绿灯删除有效断言、扩大容差或跳过必需检查。
   测试本身确有错误时，先说明需求依据和错误证据，再修正测试。
5. 结果区分：实际通过、实际失败、跳过、未运行、环境阻塞。
   固定模型、真实 Docker 和真实模型评测分别报告。
6. 关键通过条件、角色权限、预算和终态由服务端强制检查，不能只写在提示词里。
7. 更新 docs/multi-agent-execution-log.md：任务编号、当前状态、变更文件、
   检查命令、环境、退出码、统计、证据位置、未解决问题和下一步。
   记录提交及相关未提交差异的标识，不能把 HEAD 相同当作源码相同。
8. 如果缺少外部条件，先完成不受影响部分，再报告具体阻塞及所需输入。
   不重复确认已授权的实现和可逆修复；改变产品范围或验收标准时明确说明影响。

首版沿用计划范围：一个主 Agent、一个代码子 Agent、现有 Go 沙箱，
三个固定场景，首次生成后最多两次修复，通过现有 Go 任务接口接入。
只执行当前步骤及其必要修复，结尾给出完成项、实际证据和剩余项。
真实模型评测必须使用我明确给出的累计费用上限；尚无上限时完成离线准备。
```

执行记录在 S0 中创建，本次编制提示词不创建“开发已开始”的记录。日志和报告保存最小必要信息，配置凭据不写入证据。

**S0：建立可信基线**

容易出错：新版目录、旧本地修改目录和工作区根目录各自有 Git 状态，直接从当前目录运行命令可能检查错仓库。旧实现可能包含新版本没有的能力，整文件复制会覆盖新上下文代码。README 或旧验收报告中的通过数字也不能说明当前机器已经通过。

必须拿到：实际仓库路径、HEAD、未提交差异、测试环境、测试命令及结果、Docker 可用性；旧实现逐项复用意见。

```text
执行 S0（T01–T03）。确认实际仓库根目录、HEAD、分支和未提交改动，
记录是否仍以 1ea7e6b 为基线；若已经有后续开发，不回退，也不重新覆盖。
检查当前依赖、Python、Docker 和与 Go 流程有关的测试配置。
选择不会调用付费模型的基线检查，实际运行并记录结果。

只读分析旧目录 AI-Robot-FastAPI-LangChain-RAG-CrewAI-Agent- 中的多 Agent
实现及测试，逐项列出可复用逻辑和与新版接口不兼容之处，不复制整个模块。
创建执行记录。缺少依赖或 Docker 时标记阻塞，继续完成代码与契约分析。
本步完成标准是基线可信、复用范围明确；不要把历史报告写成本次测试结果。
```

**S1：先明确契约和服务器判定**

容易出错：字段存在不等于含义完整；模型可能返回 `approve` 但同时列出阻断问题。将模型提供的 hash 直接信任，仍会接受旧源码审查。`requirements_complete` 最多证明必要条目有结果，不能独自证明语义正确。

必须拿到：验证失败即不能通过的反例、hash 不匹配拒绝的反例、非法审查拒绝的反例，以及新旧报告兼容策略。

```text
执行 S1（T04–T06）。先列状态流转和服务端不变量，再实现数据契约、
配置及可独立测试的判定函数。模型只能提出意见，不能直接设置最终成功状态。

服务端根据最终待验证文件计算 artifact_hash，范围包含注入后的可信验收测试；
验证报告和审查报告均绑定它，后续文件变化使旧结论失效。
通过条件必须同时检查验证通过、当前版本审查通过、必要需求检查完整、
没有阻断问题。明确“字段完整”与“需求语义正确”各由什么证据支持。

补充：机器验证失败但模型 approve、approve 同时含 blocking、hash 不匹配、
缺失必要需求、非法配置等拒绝用例。新报告字段考虑旧存储数据的默认值。
本步不扩展新的代码场景或执行权限。
```

**S2：把角色边界做成可测试组件**

容易出错：把原生成函数改名就宣称多 Agent 完成；通过全局消息列表传递上下文，导致不同任务相互污染；审查只读取代码子 Agent 的总结，遗漏源码和原始用户限制；把模型自写测试也全部冻结，导致无法修复测试本身的缺陷。

必须拿到：主、子模型分别可注入；能检查各自实际收到的消息；任务之间隔离；服务器测试可信，而模型生成的测试允许合理修复。

```text
执行 S2（T07–T11）。实现可独立调用、独立注入模型的主 Agent 和代码子 Agent。
主 Agent 负责计划及审查；代码子 Agent 负责首次生成和修复。允许共用模型，
但职责、提示词和任务上下文必须分开，模型配置与实际调用记录保持一致。

任务交接保留原始需求、固定接口、必要参考资料；修复交接再加当前完整代码、
真实验证报告和具体问题。主 Agent 必须审查代码及证据，不能只信子 Agent 总结。
延续已有围栏解析与源码校验；冻结服务器验收测试，允许修复模型生成的测试。
结构或解析失败需记录可行动错误，并准备接入全局重试预算。

用两个独立可注入模型验证消息内容、角色调用边界及跨任务隔离。
如果本步只有固定的角色调用，准确描述自主能力，不宣称具有尚未实现的自由规划工具循环。
```

**S3：使审查真正控制修复闭环**

容易出错：代码已测试通过，就绕过审查节点结束；给修复 Agent 的只有“失败了，请重试”；修复后复用上轮通过报告；将 Docker 不可用也交给模型反复修代码。

必须拿到：测试通过但审查失败时确实重写代码；新产物重新验证；环境错误直接终止；主 Agent 输出的修复要求完整传入子 Agent。

```text
执行 S3（T12–T14）。将两个 Agent 接入现有图与 Docker 验证器。
实现“生成→产物校验→验证→主 Agent 审查→通过或修复”的业务闭环。
即使机器测试通过，只要有阻断性需求问题，也必须进入修复或明确失败。
机器验证失败时，模型 approve 不能覆盖失败；所有最终路由由服务端判定。

RepairRequest 必须携带原需求、当前完整源码、实际错误日志、问题 ID 和修复要求。
每次有效修改重新验证并重新审查，不复用旧 hash 的报告。
区分代码失败、代码测试超时与沙箱级环境故障；环境不可用不触发代码修复。

至少用固定模型跑通首次通过、编译失败后修复通过、测试通过但需求审查失败、
修复耗尽、环境不可用五条路径，并检查实际传给子 Agent 的反馈。
```

**S4：统一预算、截止时间和终止行为**

容易出错：只统计成功返回的模型调用，漏掉请求失败、解析重试、主 Agent 审查和最终总结；各 Agent 各有一个重试额度，总数超过计划；每一轮都重置 360 秒；吞掉取消异常后继续工作。账本“记了数”也不等于发送前真正阻止了请求。

必须拿到：达到上限后底层客户端没有第 9 次调用；共享重试最多一次；同一个总截止时间贯穿任务；活动调用和容器可终止。

```text
执行 S4（T15）。建立全任务共享的预算对象，在每次请求发送前占用额度，
失败请求也计数，关闭 SDK 隐式重试。初始上限按计划：正常最多 7 次模型调用，
共享异常重试最多 1 次，总计最多 8 次，业务修复最多 2 轮，沙箱验证最多 3 次。
禁止角色各自额外获得重试额度；任何额外 LLM 总结也必须计入，优先复用审查摘要。

全任务使用一个截止时间，阶段上限受剩余时间约束。为清理定义有界时间，
说明它是否包含在总耗时上界中；删除容器请求已发出不等于已确认删除。
不能把取消当作普通错误吞掉，也不能因刷新计数器继续执行。
仍有阻断问题却返回相同产物时停止；服务商未返回用量时保持未知。

用可计数的模型客户端和验证器检查边界、失败重试、取消、超时及并发任务隔离，
断言超限后没有后续外部调用，而不只是断言最终 JSON 的计数字段。
```

**S5：统一接口、保存中间状态并处理兼容**

容易出错：JSON 与 SSE 分别实现循环而逐渐分歧；只保存最终成功报告，取消时丢失已花费调用；嵌套报告新增必填字段使旧数据无法读取；缺少账户或会话校验。

必须拿到：相同输入下两入口业务结果一致；历史报告可读；取消各阶段后能查询已有证据；跨账户不可访问。

```text
执行 S5（T16–T19）。沿用同一个业务执行流生成 JSON 和 SSE 结果，
主模型、代码模型、检索器和验证器均可独立注入。
持久化计划、每轮源码和 hash、验证、审查、角色用量、停止原因及终态。
使用代表性的旧报告验证嵌套默认字段与读取兼容，而不只验证新对象能序列化。

在生成、审查、沙箱三个阶段分别模拟取消/超时，验证活动操作终止、
已有产物与调用记录保留、会话占用释放。延续账户隔离及同会话互斥规则。
对比 JSON/SSE 的业务字段；只排除时间、run_id 等合理变化，不能忽略失败差异。
新增事件或字段时核对现有客户端，避免把 HTTP 200 或流结束当作业务通过。
```

**S6：让界面忠实呈现执行状态**

容易出错：用假定时间推进阶段；连接关闭就显示绿色成功；旧任务晚到的事件修改当前任务；把代码和日志插入 `innerHTML`；有截图就宣称真实模型联调通过。

必须拿到：真实事件字段驱动界面；失败与提前断流正确显示；代码按文本渲染；浏览器实际检查过关键交互。

```text
执行 S6（T20–T21）。基于已实现的事件与报告展示主 Agent 委派、子 Agent 生成、
验证、审查、修复轮次、问题及终态，不增加独立猜测状态的前端工作流。
只有服务器最终 passed 才显示成功；断流、取消、超时和未知状态明确区分。
按 run_id 关联事件，旧任务不能覆盖新任务。代码、日志及模型文本安全按文本显示。

用真实报告形状的测试数据覆盖通过、修复、失败、断流及旧报告展示，
并通过浏览器实际检查。注明哪些响应被替换、哪些来自真实后端，
界面验收不能代替真实 Docker 或真实模型端到端验收。
```

**S7：用反例检查是否真的达到验收标准**

容易出错：测试只是复制实现逻辑；FakeRunner 总返回通过，掩盖沙箱路径没接上；为了通过而删断言；新增测试通过后忘记旧业务；套用修改前的测试结果。

必须拿到：A01–A18 对应的测试和结果；关键防线的反例能失败；真实 Docker 和原业务回归结果；证据对应最终代码。

```text
执行 S7（T22–T25）。按计划 A01–A18 建立验收映射，优先验证可观察行为和反例。
检查“失败代码被 approve”“过期 hash”“削弱服务端测试”“第 9 次模型调用”
是否真的被阻止；不要只复刻实现中的条件判断。
在临时副本或可靠恢复机制下，对关键防线做少量定向失效检查，
证明相关测试能发现防线被移除，并恢复后重跑；不要修改用户已有变更。

执行真实 Docker 验收及受影响的原业务回归，分开记录模型替身和真实执行结果。
Docker 缺失时标记未验证，完成其他测试但不勾选真实沙箱通过。
测试失败先定位，保留有效断言；测试本身错误则给出需求依据。
最后一次实现修改后运行受影响检查，并记录源码标识、命令、退出码和统计。
```

**S8：评价效果时固定比较条件**

容易出错：把主 Agent 的 `approve` 当独立质量标签；给多 Agent 更多调用后只报告成功率；根据留出结果反复调提示词；删除失败重跑；未知 Token 按零计算；把固定模型测试宣称为真实模型能力。

必须拿到：冻结配置和数据；独立验收标准；完整失败记录；真实用量及未知部分；可解释的成本和延迟比较。

```text
执行 S8（T26–T27）。先固定样本、开发/留出划分、独立评分规则、模型和运行参数，
再运行比较。主 Agent 的 approve 不能作为真实正确性标签；使用独立测试和需求检查表。
特别检查原流程最多 3 次生成与新流程最多 8 次总调用的差异：
明确原样流程对比和相同预算上限对比的设置，记录实际调用、费用及时间，
不能把更多资源产生的收益直接归因为多 Agent，也不能悄悄改写基线。

调试只使用开发集；留出集固定后不据其结果反复调参再声称独立验证。
记录失败、中断和重跑原因，保留原尝试；未知用量不得补零。
先运行离线与固定模型评测。只有已有真实模型凭据和我明确给出的累计费用上限时，
才执行收费评测；没有则完成脚本、预算校验和待运行清单。
最终报告质量、误批准/误拒绝、修复率、P50/P95、角色用量和费用。
如果证据不足或没有改善，直接说明，不为了得出提升结论改变评分规则。
```

**S9：以证据交付，而不是以任务数量交付**

容易出错：文档写着“支持恢复任务”但只实现了保存报告；代码有开关却没有验证关闭后的旧路径；照着计划把任务全勾完成；本地测试通过就声称远程 CI 通过。

必须拿到：逐项任务与证据映射、可用启动说明、实际回退结果、未完成项和效果结论。

```text
执行 S9（T28）。逐项核对 T01–T28 和 A01–A18，按实际代码与证据标记状态。
文档只说明已经实现的能力，区分报告持久化、任务恢复、普通聊天委派等不同能力。
检查配置默认值、角色模型设置、接口示例、上下文模式独立性和失败排查说明。
实际关闭多 Agent 开关，验证原 Go 流程及旧报告仍可用；回退不删除已有数据。

汇总变更、验证命令及结果、未验证内容、效果和成本结论。
本地测试、远程 CI、固定模型和真实模型结果分别说明。
没有执行的项目保持待验证或阻塞，不用“基本完成”掩盖明确缺项。
最后给出可运行版本的位置和下一项具体行动，不发布或部署未经要求的服务。
```

**每步统一交付格式**

```text
本步：Sx / 对应任务编号
状态：完成、待验证或阻塞（逐项说明）
实现：改动文件、对应行为与关键决定
证据：代码版本与相关差异标识、环境、命令、退出码、通过/失败/跳过数量、报告位置
覆盖：本步高风险反例及实际结果
剩余：未运行或失败项目、影响、原因及所需条件
下一步：满足依赖后可以执行的步骤
```

**发现偏差时使用的纠偏提示词**

```text
本次纠偏范围是：<具体问题或失败证据>。
先复现并区分实现错误、测试错误和环境问题，报告实际证据。
按原需求和验收标准修复，不通过删除断言、忽略异常或扩大预算来掩盖失败。
为此类失败保留一个能有效捕获回归的检查，验证修复及受影响功能。
更新执行记录，写明哪些旧验证结果因改动失效；不要顺带重构无关模块。
```

**中断后继续的提示词**

```text
继续实施多 Agent 计划。先读取计划、执行提示词文件、执行记录和当前 git 差异，
核对最后完成步骤的代码与证据是否仍匹配，不凭聊天摘要重做或跳过工作。
从最早未满足验收条件的步骤继续，保留已有改动。
此前失败但环境未变化时不要盲目重复；说明新证据或继续独立可做的任务。
```

**一次授权连续推进的启动提示词**

```text
请读取 /Users/xumanchun/Documents/agent项目/AI-Robot-latest/docs/multi-agent-execution-prompts.md
及其中引用的实施计划，采用总控要求，依次实施 S0–S9。
每步落实代码、必要测试和证据记录，修复本步问题后再推进依赖步骤。
在已有授权范围内自主完成，不在每步结束后重复询问是否继续。
遇到外部条件不足时保留未验证状态，并继续其他可以完成的工作。
真实模型收费评测的累计费用上限：未指定，先完成离线准备。
最终区分已实现、已验证、待验证和阻塞项。
```

如需收费评测，用户可把最后的费用一行改为明确币种和金额；不是按每阶段或每次重跑重新获得额度。普通逐步执行时，复制总控提示词及当前一个步骤即可，无需把所有步骤长文反复粘贴。

方法参考：OpenAI [Codex Prompting Guide](https://developers.openai.com/cookbook/examples/gpt-5/codex_prompting_guide) 对实施、验证与失败处理的指导，以及 [Testing Agent Skills Systematically with Evals](https://developers.openai.com/blog/eval-skills) 对可测完成条件和运行证据的指导。具体步骤、风险及预算来自本项目计划与代码分析，并非官方对本项目效果的保证。
